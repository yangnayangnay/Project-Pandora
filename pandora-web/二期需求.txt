# Pandora 二阶段开发指导 Prompt

你是一名熟悉 Android 原生开发、Vue、Spring Boot、数据库设计及产品交互设计的资深开发工程师。请基于现有 **Pandora 智能掌上工作系统**，实现二阶段的 **CRM 客户管理与人事业务协同功能**。

你的任务是先理解现有项目，再完成可运行、可验证、风格统一的增量开发。不要重新创建一个独立系统，不要只做静态页面，也不要把未完成的接口、模拟数据或占位功能描述为已完成。同时要记得Openspec框架的使用。

## 一、项目基础与不可破坏的规则

项目目录：`D:\panduola`。

当前项目主要包括：

- Android 手机端：Java、XML、Material 组件。
- 管理员 Web 端：Vue 3、Element Plus。
- 后端：Spring Boot、JdbcTemplate、RESTful API。
- 当前主要数据库：H2，项目中也存在其他数据库结构与配置。
- 已有功能：人员及组织管理、任务派发与审核、多负责人任务、日志与评论、事项日历、通知、通讯录、个人资料及主题背景。

以上用于帮助定位，具体实现以实际代码为准。

开始开发前必须：

1. 阅读适用的 `AGENTS.md`。
2. 检查当前分支、未提交修改及前后端接口。
3. 梳理现有人员、组织、权限、任务、通知、附件及数据库迁移能力。
4. 复用已有组件与规则，不重复开发，不做无关重构。
5. 核对客户端实际连接本机还是云端，区分“源码修改完成”和“线上已生效”。

保留以下现有业务约束：

- 系统有且仅有一个系统管理员；管理员身份不能通过业务岗位调整产生。
- 创始人不强制归属部门，部门负责人不强制归属团队。
- 直接上级按岗位及组织信息自动确定。
- 已有账号、密码、人员资料、任务、日志和事项不得被初始化脚本覆盖。
- 原有任务的多人负责人、审核和状态规则继续有效。
- 股东、运营合伙人、资源合伙人等业务身份，不直接等同于系统管理员或现有组织岗位。

如发现当前源码与这些规则不一致，先指出具体入口与影响范围，再进行必要修正。

## 二、二阶段业务目标

公司业务覆盖：

1. 订阅会员制线上商城。
2. 线下演出与活动票务，包括年卡客户。
3. 会员服务与权益交付。
4. 高端私宴。
5. 企业商业参访。
6. 线下沙龙。

当前痛点：

- 客户、会员、订单和服务记录分散。
- 查询一个客户需要寻找不同人员或翻查历史记录。
- 无法集中了解客户参与过的活动、享受过的权益及服务完成情况。
- 业务负责人、参与员工及工作记录缺少统一关联。
- 员工合同归档与到期提醒依赖人工。

二阶段目标是让 **客户、会员资格、业务记录、服务交付和参与员工可以关联查询**，并完善员工档案及合同管理。

本阶段不实现自动绩效评分、奖金计算、佣金结算或自动奖励决策，也不扩展为完整财务系统。

## 三、开发方式与需求边界

按照以下顺序推进：

1. 检查已有实现。
2. 输出简短的现状、复用点和缺口。
3. 给出与现有系统相容的数据关系、权限及页面方案。
4. 实现不依赖外部资料的基础能力。
5. 对必须由甲方确定的规则，集中提出简短问题。
6. 完成数据库、后端、前端及必要测试。

对于尚未明确的内容：

- 日常实现细节可以自行判断。
- 会员权益次数、价格、年卡扣减、营收计算、角色访问范围等业务规则，不得自行编造。
- 不要因为某个商城接口尚未提供而停止其他独立模块的开发。
- 可以整理拟定字段和页面方案供审阅，但应标明哪些属于建议，不能将其当作甲方已确认要求。
- 不要加入合同原文、语音需求中未提出的营销自动化、积分商城、优惠券、工资核算等功能。

## 四、客户与业务数据模型

请设计合理的独立实体及关联关系，不要把多个 ID 拼成字符串，也不要把全部信息塞进备注或一个无结构的大字段。

至少区分以下概念：

| 概念 | 含义 |
|---|---|
| 客户 | 公司服务的个人或企业 |
| 企业联系人 | 企业客户对应的自然人联系人，具体关系待确认 |
| 会员资格 | 客户在某业务或会员体系下的身份及有效期 |
| 权益定义 | 某类会员可享受的服务或权益 |
| 权益使用／履约记录 | 实际使用、服务办理及完成记录 |
| 业务记录 | 一次活动、参访、沙龙、私宴或其他服务业务 |
| 员工参与关系 | 业务主要负责人及其他参与员工 |
| 外部订单关联 | 商城订单及其来源标识 |
| 员工合同 | 员工劳动合同资料、期限及附件 |

设计原则：

- 同一客户可以涉及多个业务、会员资格及服务记录。
- 客户与业务根据实际关系建模，支持一项业务关联多个客户。
- 一项业务有主要负责人及多个参与员工。
- 员工账号与客户档案是不同概念，不混用同一张用户表。
- 业务记录与任务是不同概念；可关联已有任务，但不能用任务字段直接替代完整业务资料。
- 保存来源与外部标识，支持追溯和同步去重。
- 迁移必须兼容已有数据；运行中的正常数据库不能通过删库重建升级。

## 五、具体功能要求

### 1. 统一客户管理

支持个人客户、企业客户的查询及档案维护。

客户详情应在一个连贯页面中呈现：

- 基础资料。
- 会员资格及有效期。
- 相关订单与消费记录，前提是数据已接入。
- 参加过的活动和业务。
- 权益使用及服务交付记录。
- 对应业务负责人及参与人员。

支持必要的名称／联系方式搜索和类型筛选。

客户识别、去重和合并规则需明确，不能只凭同名自动合并，不能在合并时丢失历史关联。

### 2. 会员与权益管理

区分商城会员、会员服务及演出年卡等不同体系，不强行合并为单一等级。

支持记录资格、有效期、可享权益以及实际使用和完成情况。

会员等级、权益清单、使用次数、扣减、续期和退款返还等规则，根据甲方资料实施。资料缺失时不要写死推测规则。

### 3. 业务与服务记录

支持按业务类型查询开展情况，进入详情可以查看：

- 业务基本信息。
- 关联客户。
- 主要负责人。
- 参与员工。
- 开展与完成情况。
- 相关服务记录。

从客户和员工页面均可回查对应业务。

需要统计时，先明确统计口径。订单金额、实收金额、退款和营收不是同一个概念，不能直接混算。

### 4. 商城数据衔接

先检查项目是否已有相关接入。

获得接口文档后，再实现客户、会员和订单同步，并覆盖：

- 外部客户与本地客户的关联。
- 外部订单唯一标识。
- 重复同步不重复写入。
- 失败重试及错误反馈。
- 历史数据范围与增量更新。
- 必要的数据来源及同步时间展示。

未取得接口资料时，可以完成内部模型及接入边界，但不要制造虚假的同步成功记录。

### 5. 员工档案与合同

扩展现有员工资料，不另建一套重复的人员管理。

支持保存必要的职责信息、合同资料、期限及附件，并关联现有组织岗位。

合同到期提醒复用通知体系。提前多久提醒、通知谁、是否重复提醒及续签处理规则，需要确认。

合同附件须经过权限校验，不能因为知道文件地址就可直接下载。

### 6. 工作参与记录

保留员工负责或参与过的业务及服务记录，便于年度回顾和人工绩效参考。

只记录事实和完成情况，不自动生成绩效等级、奖金或奖励结论。

## 六、权限要求

先输出功能、字段与数据范围权限矩阵，再按确认结果实施。

需要区分的业务身份：

- 创始人。
- 股权投资股东。
- 运营合伙人。
- 资源合伙人。
- 行政财务。
- 业务及运营员工。

权限应分别考虑：

1. 能否进入功能。
2. 能查看哪些客户和业务。
3. 能查看哪些字段。
4. 能否创建、编辑或删除。
5. 能否查看合同、订单及营收信息。
6. 能否下载附件。

不得默认：

- 普通员工可以查看全公司客户。
- 股东或合伙人拥有全部客户、人事和财务资料权限。
- 系统管理员必然具有所有业务资料的阅读权限。

前后端必须同步控制。列表、搜索、详情、关联查询和附件下载都要验证，不能只隐藏按钮。

## 七、UI 与交互设计指导

### 1. 整体视觉方向

保持 Pandora 现有的暖色办公风格：

- 米白、暖灰作为基础背景。
- 棕色作为主要操作色。
- 使用现有主题色、字号、圆角和间距资源。
- 保留纯色简约、商务办公、元气可爱及昼夜模式兼容。
- 主要操作有清晰层级，避免所有按钮都使用重色。

整体应当清楚、克制、有温度，适合日常办公。不要做成宣传页，不使用大面积渐变、装饰图和夸张动效挤占业务空间。

### 2. 页面信息结构

客户详情可以采用以下信息层级：

- 顶部：客户名称、类型、关键资格和当前状态。
- 中部：基础资料、会员权益、相关业务、订单／服务记录等分区。
- 记录区：按时间呈现关键业务和服务记录，便于追溯。
- 操作区：突出当前主要动作，次要操作放在合理位置。

这是布局指导，不代表新增未经确认的字段或统计指标。

避免将所有字段堆成一个超长表单，也不要把每一行文字都包进独立卡片。

### 3. Android 手机端

- 沿用现有导航，入口优先在现有“公司”等相关区域整合；确需改变底部导航时先说明。
- 信息以列表和详情为主，避免照搬桌面宽表格。
- 搜索与筛选可收起，常用筛选清晰可达。
- 人员多选复用现有按部门、团队搜索的选择能力。
- 表单按业务分组，键盘弹出后仍能看到当前输入和保存操作。
- 点击其他选择控件时及时清除文本焦点，避免页面自动滚回输入框。
- 使用现有可靠返回键实现，正确处理系统状态栏与安全区域，避免重复留白或点击区域错位。
- 常规触摸目标至少48dp；长文本可展开或进入详情，不撑坏布局。
- 保留未保存修改提示，并区分新建草稿和编辑状态。
- 主要动作使用与现有页面一致的棕底白字及轻微按压反馈。
- 不对全项目按钮统一新增边框；只对本轮新增界面和必要控件做局部设计。

### 4. 管理员 Web 端

- 复用现有 Element Plus 表格、筛选、弹窗及抽屉。
- 查询页保持清晰的搜索区、操作区和数据区。
- 内容多的详情优先使用有分区的详情页或抽屉，避免狭窄弹窗承载全部信息。
- 表格使用合理列宽，长内容省略后可查看全文。
- 状态、会员类型与业务类型使用克制的标签，不用颜色承担唯一含义。
- 表单必填、格式提示和错误位置明确，保存过程中防止重复提交。
- 权限受限、加载中、加载失败、无数据等状态均有完整设计。
- Web 与手机端的数据规则相同，布局根据各端特点调整。

### 5. 主题与可读性

- 正文与背景保持足够反差，夜间模式逐项检查。
- 背景插画和照片不得干扰表格、表单及合同资料阅读。
- 不同页面使用一致的间距和组件规则。
- 优先使用现有线性图标，不用表情符号代替正式导航图标。
- 动效用于反馈状态和保持位置感，不让用户等待不必要的装饰动画。
